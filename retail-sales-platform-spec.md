## CORE — Phases 0–3 (finish first, then stop and report)

### Phase 0 — Setup

### Phase 1 — Pipeline into PostgreSQL (`pipeline/`)
**Transform (cleaning)**, applied in order, producing a cleaning log `step | rows_before | rows_after | removed | pct | reason`:
1. Drop null `Customer ID`.
2. Separate cancellations (`Invoice` starts with "C") into their own table. Compute the cancellation rate.
3. Drop `Quantity <= 0` and `Price <= 0`.
4. Drop exact duplicates.
5. Drop non-product `StockCode`s (POST, DOT, M, D, C2, BANK CHARGES, AMAZONFEE, PADS, ADJUST*, TEST*). List exactly which were found.
6. Add `revenue = quantity * price`.

**Load:** a star schema in `sql/schema.sql`: `fact_sales`, `fact_cancellations`, `dim_customer`, `dim_product`, `dim_date`. Loads are **idempotent**, so running the pipeline twice yields identical row counts (truncate-and-load or upsert). Add indexes on the join and filter columns.

**Quality checks (`quality.py`)**, run automatically at the end of the pipeline and failing loudly:
- Row-count reconciliation: rows loaded equal rows after the transform.
- Revenue reconciliation: the SUM in Postgres equals the SUM in pandas (to the penny).
- No nulls in key columns, positive quantities and prices, unique keys.
- **Schema drift:** expected columns and dtypes match a stored contract.
- **Volume anomaly:** flag any month whose row count deviates more than 3 standard deviations from the rolling median.
- Freshness: report the max `invoice_date` loaded.

Write a quality report to `RESULTS.md`.

**Tests (`tests/`):** pytest unit tests for each cleaning rule on tiny hand-made DataFrames, plus an idempotency test. Add a GitHub Actions workflow running `pytest` on push.

**Verify:** run the pipeline twice; the counts are identical and all checks pass.

### Phase 2 — SQL analysis (`sql/analysis/`, run from a notebook)
1. Monthly revenue, orders and active customers. **Chart.**
2. Top 10 countries by revenue with % share.
3. Top 3 products per country: `ROW_NUMBER() OVER (PARTITION BY country ORDER BY revenue DESC)`.
4. Revenue concentration: % of revenue from the top 1%, 10% and 20% of customers. **Chart:** cumulative share curve.
5. Month-over-month customer retention.

### Phase 3 — Multi-factor customer tiering (`tiering/`)
This mirrors Apple's "Business Tiering" work: combine several weighted inputs into one classification, validate it, and explain it.

1. **Time split:** features use data **before 2011-06-01**. Validation uses outcomes from **2011-06-01 to 2011-11-30**.
2. **Features per customer**, pre-cutoff: recency, frequency, monetary, tenure, average order value, product breadth (distinct products), cancellation rate, and purchase regularity (std of days between orders).
3. **Composite score:** normalize each feature to a 0–1 percentile rank (invert recency and cancellation rate). Weighted sum with **documented weights** (start with R 0.25, F 0.25, M 0.30, breadth 0.10, cancellation 0.10).
4. **Tiers:** Tier 1 = top 10%, Tier 2 = next 20%, Tier 3 = next 30%, Tier 4 = bottom 40%.
5. **Validation, the key step:**
   - Future revenue by tier: mean, median and share of total. A good tiering model is monotonic, so Tier 1 > Tier 2 > Tier 3 > Tier 4.
   - Spearman correlation between the score and future revenue.
   - Compare against baselines: monetary-only ranking, and an equal-weights score.
   - **Data-driven weights:** fit a `LogisticRegression` (target = customer is in the top 20% of future revenue) or `HistGradientBoostingClassifier` on standardized features, and compare its ranking quality (Spearman, share of future revenue captured by the top 10%) against the hand-weighted score. Report honestly whichever wins.
   - **Weight sensitivity:** vary each weight ±50%. How many customers change tier?
6. **Explainability:** a function `explain(customer_id)` that returns each feature's contribution to the score plus the tier, as a readable breakdown. Include 2 worked examples in the README.
7. **Charts:** future revenue by tier (bars), and the share of future revenue captured vs % of customers targeted (score vs baselines).

## EXTENSION — Phase 4: Evaluated AI Analyst (`analyst/`)

**Goal:** answer business questions in natural language by generating SQL against the warehouse, and **measure how often it is right, including how often it is confidently wrong.**

1. **Agent (`agent.py`):** Gemini (e.g. `gemini-2.5-flash` or the current equivalent) is given the schema and table descriptions, generates **read-only** SQL, and the result is executed and returned with a natural-language answer.
   - Guardrails: allow `SELECT` only (reject anything else), run under a read-only Postgres role, set a statement timeout, and cap row limits.
   - Retry once on a SQL error, feeding the error message back to the model.
   - Structured logging (question, SQL, latency, success) to a JSONL file. Cache repeated questions.
   - **Abstention:** the model may answer "I can't answer that from this data." Questions that are out of scope must be refused.
2. **Ground-truth set (`eval_set.yaml`):** 30–40 questions, each with a **hand-written reference SQL**. Mix easy (totals), medium (joins, group by), hard (window functions, time comparisons), and **5–8 unanswerable questions** (e.g. "What was profit margin?" when there's no cost data; "Which salesperson…?" when there's no such column).
3. **Evaluation (`evaluate.py`):**
   - **Execution accuracy:** the agent's result set matches the reference result (order-insensitive, numeric tolerance).
   - **Abstention accuracy:** it correctly refuses the unanswerable questions.
   - **Confidently wrong rate:** it answered (did not abstain) and the answer was wrong. **This is the headline metric.**
   - Accuracy by difficulty tier, plus latency p50/p95.
   - **One improvement iteration:** add a mitigation (few-shot examples, column descriptions, or a self-check step that verifies the SQL result before answering), re-run, and report the before/after.
4. **Optional:** a FastAPI endpoint `POST /ask`.
5. Update the README (add an AI Analyst section with a results table) and RESULTS.md. Commit.
